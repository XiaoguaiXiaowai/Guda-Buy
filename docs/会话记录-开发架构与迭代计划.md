本次会话中替用户拍板的技术口径（已在文末向用户说明，可随时调整）：

1. 引入 Celery + Beat（复用 Redis 作 broker），用于订单 30 分钟超时取消、券到期、通知投递。
2. 购物车仅登录可用，不做游客本地购物车合并。
3. 一期一张订单只能使用一张券，不支持叠加。
4. 模拟支付通过 HMAC-SHA256 签名回调完成，支付单幂等。
5. 外部标识统一用 `public_id`（32 位 UUID），内部自增 ID 不对外暴露。

每个迭代包含：

- 目标、功能范围、明确不包含项（防范围蔓延）
- 独立部署验证场景表（编号 `V{迭代}-N`，含操作与可观测通过标准）
- 任务表：任务 ID、交付物、验证清单、通过标准、状态
- 验收登记表：验收结论、验收人、验收日期、证据引用、遗留问题

验收机制要点：

- 任务状态：`TODO → DOING → REVIEW → VERIFIED`，另有 `BLOCKED`、`WAIVED`
- 交叉验收：由非开发者本人验收；部署验证通过后 1 个工作日内登记，禁止批量补登
- 证据至少一项：PR/commit、测试结果与覆盖率、curl 请求响应、页面截图、部署记录
- 不通过需开缺陷单（P0–P3）；有条件通过仅限 P2/P3；P0/P1 不得通过
- 迭代出口门禁 8 项：功能、质量、契约、数据、部署、回归抽测、登记完成率、文档
- 另有全局验收汇总表、需求追溯矩阵（F-01～F-12 → 迭代）、变更与阻塞处理规则

为满足"每迭代可独立部署"，对跨迭代职责做了明确切分：

1. I5 下单时只创建 `PENDING` 支付单，I6 才实现模拟支付、签名回调与收银台；I5 的发货/确认收货以 service 集成测试验证，页面端到端放在 I6（V6-8）。
2. 通知模块 I8 才交付，I5/I6/I7 只预留事件挂点并在文档中标注，避免验收口径失真。

### 4.2 会话归属不在 Guda-Buy 分组下

用户指出截图现象：Trae 侧边栏中 `在线电商网站技术架构文档` 会话挂在旧项目 `GUDA在线电商网站` 分组下，而非 `Guda-Buy`。

结论：

- 该分组按**会话打开时的本地文件夹路径**归类；旧路径已不存在，故会话仍显示在旧分组
- 会话列表由客户端/账号侧维护，不属于仓库文件，无法通过代码或脚本可靠迁移（改了状态可能损坏客户端数据，故未尝试）
- 已向用户给出三种方案：
  1. 客户端内右键该会话，查看是否有「移动到项目」入口（唯一无损方式）
  2. 保留旧分组，手动指定工作目录继续使用
  3. 在 Guda-Buy 下新建会话，通过项目内文档接续上下文（即本文件的用途）
- 另建议移除已失效的 `GUDA在线电商网站` 与空的 `GUDA-Online-E-commerce-Website` 两个项目条目

注：当前会话默认 cwd 仍指向已不存在的旧路径，直接执行 shell 会失败；本次会话中通过显式指定 `cwd=/Users/lijia/Documents/AI全栈开发高级班261025/Guda-Buy` 绕过。
