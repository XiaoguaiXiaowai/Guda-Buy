## 4. 关键实现约定（I10 及以后沿用）

1. 评价唯一性由 `Review.order` OneToOne 保证，一单一评；订单多商品时提交必须带 `sku_public_id`，前端从可评状态接口的 `items` 渲染选择器。
2. 可评窗口以 `order.completed_at + REVIEW_WINDOW_DAYS` 计算；仅 `COMPLETED` 且未过期可评。
3. 状态机单向：`PENDING → APPROVED / REJECTED`；仅 `PENDING` 可审核，非法流转 409；驳回后用户重提覆盖原记录并回到 `PENDING`。
4. 图片同步落盘至 `reviews/{review.public_id}/`；白名单 `jpg/jpeg/png/webp`，单张 5MB、最长边 4096px；重提保留已上传图片并计入 3 张上限。
5. 公开列表只返回 `APPROVED`；匿名评价昵称脱敏、头像不返回，任何出参不得包含 `username`。
6. 评分聚合只统计 `APPROVED`；审核通过/驳回在事务 `on_commit` 中失效商品详情缓存（`catalog.cache.bump_product_version`）。
7. 审核结果消息统一走 `notifications.create_notification`，评价模块不直接写消息表；消息失败以 `try/except` 隔离，不影响审核。
8. 用户资源越权统一返回 404，避免通过错误码探测他人订单/评价是否存在。

## 5. 已知限制与注意事项

- Playwright 未脚本化，本轮使用浏览器自动化（browser-use）执行 V9-4/V9-5 主链路；接口规则由 32 例 pytest 覆盖。
- P95 未做压测；公开评价列表固定 4 条 SQL（商品存在性、count、分页、图片预取）。
- 浏览器流程未实际上传图片，图片上传链路由 pytest 覆盖（含 3 张上限与非法文件）。
- 敏感词当前仅记录 WARNING 并进入人工审核（本期所有评价均人工审核），未做前端提示或自动替换。
- 评价图片为同步处理，未接入异步压缩；大图会占用请求时长。
- 审核结果消息类型为 `SYSTEM`，点击跳转订单详情（`biz_type=ORDER`）；如需直达评价页，I10 可扩展消息路由。
- 本地前端使用 `http://localhost:5173`；`127.0.0.1` 可能因 CORS/refresh 白名单失败。
- 验收产生订单 `GDREVIEW20261123` 与 1 条已通过评价为本地测试数据，可随时清理。
