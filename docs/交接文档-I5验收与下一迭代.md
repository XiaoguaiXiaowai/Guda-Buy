## 4. 关键实现决策（I6 必须知晓）

1. **库存锁定语义**：`available = stock - locked_stock`。下单只增加 `locked_stock`，不扣 `stock`；取消/超时回落后不恢复购物车。I6 支付成功时应同时 `stock -= qty` 且 `locked_stock -= qty`。
2. **锁顺序**：下单、取消、释放库存均按 SKU `id` 升序 `select_for_update`，避免与购物车并发交叉死锁。
3. **幂等键**：`Order(user, idempotency_key)` 唯一约束；请求指纹由“排序后的购物车项 + 地址 + 备注”哈希生成。同键同参返回原单（200），同键异参返回 409 `ORDER_IDEMPOTENT_REPLAY`。
4. **支付单**：I5 建单即生成一条 `PENDING` 支付单，`channel` 默认 `ALIPAY_MOCK`。I6 需实现“一订单同时只有一个 `PENDING`”的复用/关闭规则。
5. **地址快照**：`address_snapshot` 存下单时明文收货信息；额外增加 `Order.address_public_id` 索引列，仅用于“未完成订单引用地址禁止删除”的 422 校验（不改动已定稿 JSON 结构）。
6. **销量累加时机冲突**（需 I6 决策）：I5 按 T5.7 在**确认收货**时累加销量；而 I6 V6-2 描述“支付成功销量 +1”。两者不可同时执行，否则重复计数。当前实现以 T5.7 为准，**I6 支付成功回调不得再累加销量**，除非同时调整 T5.7 与相关测试。
7. **已完成订单没有评价字段**：评价在 I8，I6 不要提前加表。

## 6. 已知问题与风险

| 级别 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| 中 | 销量累加时机在 I5/I6 文档中存在冲突 | 若 I6 直接按 V6-2 实现会双倍计数 | I6 启动第一步先决策并更新计划表 |
| 低 | 购物车校验用 `stock`，下单校验用 `stock - locked_stock` | 高峰锁库存时购物车可能显示可结算、结算时提示库存变化 | I6 可统一为可用库存 |
| 低 | 后台订单页面未交付（I5 计划仅要求 API） | 运营需通过 API 发货 | 可在 I6 与本迭代后台支付流水一起补页面 |
| 低 | 登录前控制台有 1 条 `auth/refresh/ 403` | 既有静默刷新行为，不影响功能 | 后续可在拦截器跳过无 refresh cookie 场景 |
