## 4. 关键实现约定（I7 及以后沿用）

1. 回调校验顺序固定为：**支付单存在 → 金额一致 → 签名 → 状态机**，金额篡改优先返回 422。
2. `payment_no + amount(两位小数)` 参与签名；密钥仅来自 `PAYMENT_CALLBACK_SECRET`，不得写入代码或前端。
3. 支付成功必须在同一事务内完成：扣减 `stock`/`locked_stock`、订单转 `PAID`、支付单转 `SUCCESS`、写状态流水、关闭同订单其他 `PENDING` 单。
4. 销量只在确认收货累加，支付回调不得碰 `sales_count`。
5. 失败回调只改支付单为 `FAILED`，订单保持 `PENDING_PAYMENT`；成功回调重复到达直接返回 200，不产生副作用。
6. 一订单同时最多一张 `PENDING` 支付单；同渠道复用，换渠道关闭旧单再新建。
7. 消息通知预留点：`services._apply_success` 末尾的 `on_commit` 注释处，I8 在此写入 `ORDER_PAID` 站内消息。

- 后台支付流水仅提供 API，未做 `/admin/payments` 页面；后台订单发货页同样仍待补（均为 I5/I6 遗留，API 已就绪）。

- 本迭代不涉及退款、对账、真实渠道；退款资金与订单状态流转为后续迭代范围。
- 本地后端以 `runserver --noreload` 运行，新增路由后必须重启后端进程才会生效。

## 6. 下一迭代（I7 优惠券）接入点

1. 结算与下单新增优惠券抵扣后，`order.payable_amount` 即为支付唯一金额来源，支付模块无需改动。
2. 支付发起前如需校验券状态，应在下单事务内完成锁券，支付回调只认 `payable_amount`。
3. 取消订单/超时取消时需同步退还优惠券，并关闭 `PENDING` 支付单（`cancel_order` 已有支付单关闭逻辑）。
4. I8 通知接入时，在支付成功事务的 `on_commit` 中写入消息，避免事务回滚产生脏消息。
