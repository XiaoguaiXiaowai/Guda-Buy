## 1. 文档说明

### 1.1 目的

本文档为 GUDA 在线电商网站的技术基线，用于统一各端开发口径。任何实现与本文档冲突时，以本文档为准；确需变更的，先修改本文档并升版本号，再改代码。

### 1.2 术语表

| 术语 | 含义 |
| --- | --- |
| SPU | 标准商品单元，描述"商品"本身（如某款 T 恤） |
| SKU | 最小库存单元，描述可售卖的具体规格（如红色 L 码） |
| CMS | 内容管理系统，管理页面、栏目、公告、轮播等运营内容 |
| JWT | JSON Web Token，本项目用于无状态身份认证 |
| RBAC | 基于角色的访问控制 |
| 幂等 | 同一请求重复提交，业务结果只生效一次 |
| 软删除 | 仅标记删除状态，不物理删除数据 |

### 1.3 强制约束（不可协商项）

1. 前端 Vue 3，后端 Django 5.2 + DRF，认证采用 JWT。
2. 数据库 MariaDB，语法与驱动保持 MySQL 兼容。
3. 缓存使用 Redis。
4. 不使用 Docker / 容器化，采用宿主机直接部署。
5. 开发环境 macOS，生产环境 Ubuntu 24.04 LTS。
6. 支付模块只实现业务流程与状态流转，不接入任何真实支付渠道。

## 2. 项目需求

### 2.1 项目定位

GUDA 是一个单商户 B2C 在线电商网站，面向 Web 端（桌面优先、移动端自适应）。系统需覆盖"商品浏览 → 加购 → 下单 → 模拟支付 → 订单履约 → 售后评价"的完整闭环，同时提供内容运营（CMS）、营销（优惠券）、用户触达（站内消息）与服务（在线客服）能力。

### 2.2 角色与权限矩阵

| 角色 | 说明 | 关键权限 |
| --- | --- | --- |
| 游客 | 未登录用户 | 浏览商品、分类、CMS 页面、注册登录 |
| 会员（customer） | 注册用户 | 购物车、下单、支付、订单、评价、优惠券领取、消息、客服会话、个人中心 |
| 客服（support） | 后台坐席 | 客服工作台、会话接管与回复、订单只读查询、用户基础信息只读 |
| 运营（operator） | 内容与商品运营 | 商品与 SKU 管理、CMS 管理、优惠券创建、评价审核、订单查询 |
| 管理员（admin） | 系统管理员 | 全部权限、用户与角色管理、系统配置、审计日志 |

权限矩阵（✓ = 允许，— = 禁止）：

| 能力 | 游客 | 会员 | 客服 | 运营 | 管理员 |
| --- | --- | --- | --- | --- | --- |
| 浏览商品 / CMS | ✓ | ✓ | ✓ | ✓ | ✓ |
| 购物车 / 下单 / 支付 | — | ✓ | — | — | ✓ |
| 查看自己的订单 | — | ✓ | — | — | ✓ |
| 查看全部订单 | — | — | 只读 | 只读 | ✓ |
| 发表评价 | — | ✓（限已完成订单） | — | — | ✓ |
| 评价审核 | — | — | — | ✓ | ✓ |
| 商品 / SKU 维护 | — | — | — | ✓ | ✓ |
| CMS 维护 | — | — | — | ✓ | ✓ |
| 优惠券创建 | — | — | — | ✓ | ✓ |
| 客服会话回复 | — | — | ✓ | — | ✓ |
| 用户与角色管理 | — | — | — | — | ✓ |

角色实现方式：Django 内置 `Group` 承载角色，权限点使用 Django `Permission`（`app_label.codename`），后台接口统一走 `IsAuthenticated + DjangoModelPermissions` 或自定义 `RolePermission`。禁止在视图里硬编码用户名判断。

### 2.3 功能需求清单

| 编号 | 模块 | 需求要点 | 验收摘要 |
| --- | --- | --- | --- |
| F-01 | 基础框架 | 前后端工程骨架、统一响应、统一异常、日志、配置分层、健康检查、OpenAPI 文档 | 服务可启动，`/healthz` 返回 200，接口文档可访问 |
| F-02 | 注册登录 | 邮箱/手机号注册、密码登录、JWT 签发与刷新、登出、找回密码、登录限流 | 登录返回 access/refresh，刷新可续期，登出后 refresh 失效 |
| F-03 | 商品展示 | 分类树、SPU/SKU、商品列表（分页/筛选/排序/搜索）、商品详情、上下架 | 列表分页正确，下架商品前台不可见 |
| F-04 | 购物车 | 加购、改数量、勾选、删除、清空、金额试算 | 金额与 SKU 单价一致，超库存给出明确提示 |
| F-05 | 支付（流程演示） | 生成支付单、选择"模拟支付"、支付结果回调、支付状态查询 | 支付单状态流转正确，重复回调不重复改单 |
| F-06 | 订单系统 | 下单、订单列表/详情、取消、确认收货、超时自动取消、库存扣减与释放 | 订单状态机合法流转，库存不超卖、不泄漏 |
| F-07 | 用户通知 | 站内消息列表、未读数、标记已读、全部已读、业务事件自动通知 | 下单/发货/支付成功均产生消息，未读数准确 |
| F-08 | 用户中心 | 交易记录、地址管理（增删改查、默认地址唯一）、个人信息维护 | 默认地址全局唯一，交易记录与订单一致 |
| F-09 | CMS | 栏目、页面、公告、轮播位管理，富文本内容，发布/下线 | 未发布内容前台不可见，发布后缓存即时失效 |
| F-10 | 用户评价 | 星级 + 文字 + 图片（可选）、按商品聚合展示、审核状态 | 仅已完成订单可评，一单一评，审核通过后展示 |
| F-11 | 优惠券 | 满减/折扣/免邮三类券，领取限制、适用范围、下单核销、取消退还 | 优惠金额计算可复现，券不可超领、不可重复核销 |
| F-12 | 客服系统 | 会话创建、消息收发、客服接管、历史记录、在线状态 | 消息按时间有序，会话可被客服接管并回复 |

### 2.4 非功能需求

| 类别 | 指标 |
| --- | --- |
| 性能 | 核心读接口 P95 ≤ 300ms，写接口 P95 ≤ 500ms；首页首屏（4G 网络）≤ 2s |
| 并发 | 单机支撑 300 并发在线用户、峰值 50 QPS（架构层面支持横向扩展，本期不横向部署） |
| 可用性 | 单机部署，服务异常由 systemd 自动拉起；月度可用率目标 ≥ 99% |
| 安全 | 全站 HTTPS；密码 Argon2 哈希；接口限流；越权访问零容忍；敏感操作留审计日志 |
| 兼容性 | Chrome / Edge / Safari 最新两个大版本；分辨率 1280–2560，移动端 375px 起自适应 |
| 可维护性 | 后端核心模块单测覆盖率 ≥ 80%，前端类型检查零错误，静态检查零告警 |
| 数据 | 每日全量备份，保留 30 天；订单、支付数据只增不删（软删除） |
| 合规 | 遵循《个人信息保护法》最小必要原则，手机号等敏感信息加密存储、日志脱敏 |

### 2.5 本期不做（防止范围蔓延）

第三方真实支付、物流对接、多商户入驻、多语言、秒杀、分销、发票、退款资金原路退回（仅做退款状态流转）、容器化与 K8s。

## 3. 技术架构

### 3.1 总体架构

```
                    ┌───────────────────────────────┐
                    │  浏览器（PC / 移动端 H5）      │
                    │  Vue 3 + Vite 构建的静态资源   │
                    └───────────────┬───────────────┘
                                    │ HTTPS
                    ┌───────────────▼───────────────┐
                    │  Nginx 1.24                   │
                    │  · 静态资源直出（dist/static） │
                    │  · /media 直出                 │
                    │  · /api 反向代理（unix socket）│
                    │  · TLS 终止、gzip、限流兜底     │
                    └───────────────┬───────────────┘
                                    │
                    ┌───────────────▼───────────────┐
                    │  Gunicorn（systemd 托管）      │
                    │  Django 5.2 + DRF 3.16        │
                    │  ├─ api 层（序列化/校验/权限）  │
                    │  ├─ services 层（业务事务）     │
                    │  ├─ selectors 层（查询组装）    │
                    │  └─ tasks 层（Celery 异步任务） │
                    └───────┬───────────────┬───────┘
                            │               │
              ┌─────────────▼─────┐   ┌─────▼─────────────┐
              │ MariaDB 11.x      │   │ Redis 7.x         │
              │ 业务主数据          │   │ 缓存/限流/锁/Celery│
              └───────────────────┘   └───────────────────┘
                            │
              ┌─────────────▼─────┐
              │ 本地磁盘 media/    │
              │ 商品图、评价图、头像│
              └───────────────────┘
```

架构要点：

1. 前后端完全分离，前端只通过 `/api/v1/**` 访问后端，不共享模板。
2. 后端严格分层：`api`（协议适配）→ `services`（业务编排与事务）→ `models/selectors`（数据访问）。视图函数内不写业务规则。
3. Redis 承担缓存、限流、分布式锁与异步任务队列，不承担持久化业务数据。
4. 单机部署，但所有状态（除本地媒体文件）都不落在进程内存，保证可平滑迁移到多机。

```
│   ├── accounts/               # 用户、地址、认证

├── tests/                      # 跨 app 集成测试（按 app 也可就近放置）
└── scripts/                    # 部署与运维脚本（备份、发布）
```

单个 app 内部固定分层：

```
apps/<app>/
├── models.py            # 数据模型与不跨表的领域方法
├── selectors.py         # 复杂查询组装（只读）
├── services.py          # 业务用例、事务边界、跨模型编排（唯一写入口）
├── serializers.py       # 入参校验、出参序列化
├── permissions.py       # 该 app 的对象级权限
├── filters.py           # 列表过滤
├── api.py / views.py    # 视图（薄，只做协议转换与调用 service）
├── urls.py
├── tasks.py             # Celery 任务
├── admin.py
├── migrations/
└── tests/
```

分层规则：

| 层 | 允许做 | 禁止做 |
| --- | --- | --- |
| views / api | 认证、权限、参数校验、调用 service、组装响应 | 写事务、跨表写操作、复杂计算 |
| serializers | 字段校验、格式转换、展示字段拼装 | 发起写操作、访问 Redis |
| services | 事务、领域规则、跨模型编排、发消息/发任务 | 直接处理 HTTP 对象（request/response） |
| selectors | 查询优化（`select_related`/`prefetch_related`）、聚合 | 写操作 |
| models | 字段约束、单表领域方法、状态判断 | 跨 app 依赖、发网络请求 |

所有跨表写操作必须包在 `transaction.atomic()` 内，且事务内禁止调用外部 HTTP 或耗时操作；通知、邮件等副作用通过 `transaction.on_commit` 投递 Celery 任务。

前端约束：

1. 所有请求必须经过 `src/api` 封装，组件内禁止直接 `axios.get`。
2. Token 注入、401 刷新、错误提示、重复提交拦截统一在 Axios 拦截器处理。
3. 金额一律用字符串在前端接收，展示用工具函数格式化，禁止 `Number` 直接累加。
4. Pinia 只保存跨页面共享状态；页面内状态留在组件。
5. 路由按模块懒加载；后台路由需 `meta.roles` 校验。
6. 图片统一走懒加载与占位图，上传前压缩与类型校验。

### 3.5 部署架构

#### 3.5.1 开发环境（macOS）

| 组件 | 方式 |
| --- | --- |
| Python | 3.12，`uv venv` + `uv sync` |
| 数据库 | Homebrew `mariadb`，`brew services start mariadb`，库名 `guda_dev` |
| Redis | Homebrew `redis`，默认 6379 |
| 后端 | `python manage.py runserver 8000`（`config.settings.dev`） |
| 前端 | `pnpm dev`，Vite 5173，`/api` 代理到 `http://127.0.0.1:8000` |
| 静态/媒体 | Django 直接服务 media；不使用 Nginx |
| 异步任务 | Celery worker + beat 以 `--pool=solo` 本地运行（或 `CELERY_TASK_ALWAYS_EAGER=true` 关闭） |
| 邮件 | `EMAIL_BACKEND=console`，验证码输出到控制台 |

#### 3.5.2 生产环境（Ubuntu 24.04 LTS）

部署拓扑：Nginx（公网 443）→ Gunicorn（unix socket）→ Django；MariaDB、Redis 同机；Celery worker/beat 由独立 systemd 单元托管。

目录规范：

```
/srv/guda/
├── app/                   # 当前版本代码（git 拉取，只读运行）
├── venv/                  # 虚拟环境
├── static/                # collectstatic 产物（Nginx 直出）
├── media/                 # 用户上传（Nginx 直出，仅允许图片类型）
├── logs/                  # 应用日志（logrotate 管理）
├── backups/               # 数据库与 media 备份
└── env/.env               # 环境变量（权限 600，属主部署用户）
```

进程与系统配置基线：

| 项 | 基线 |
| --- | --- |
| 运行用户 | `guda`（非 root，无 sudo） |
| Gunicorn | `--workers 2*CPU+1 --threads 2 --timeout 60`，socket `/run/gunicorn/guda.sock`，`--max-requests 1000 --max-requests-jitter 100` |
| systemd 单元 | `guda-web.service`、`guda-celery.service`、`guda-celerybeat.service`，均 `Restart=always`，`RestartSec=3` |
| Nginx | `gzip on`；`client_max_body_size 10m`；`/api` 转发 socket；`/static`、`/media` 直出并设 `Cache-Control`；隐藏 `server_tokens` |
| TLS | Let's Encrypt 证书，HTTP 强制跳转 HTTPS，仅启用 TLS1.2/1.3 |
| 防火墙 | `ufw` 仅放行 22/80/443，数据库与 Redis 只监听 `127.0.0.1` |
| 时区 | 系统 `Asia/Shanghai`，应用 `TIME_ZONE=Asia/Shanghai`、`USE_TZ=True`，存储统一 UTC |
| 日志 | 应用日志 JSON 行格式，`logrotate` 按天切分保留 14 天；Nginx access/error 保留 30 天 |
| 备份 | 每日 02:00 `mysqldump`（含 routines/triggers）+ media 增量同步，数据库保留 30 天、media 保留 7 天 |
| 监控 | `/healthz` 供外部探活（校验 DB 与 Redis 连通），失败返回 503 |

发布方式（不属于迭代计划，仅为运行手册要点）：代码更新 → `uv sync` → `migrate` → `collectstatic` → 重启 `guda-web`/`guda-celery` → 冒烟验证 `/healthz` 与下单链路。发布前必须完成数据库备份。

### 3.6 Redis 使用规范

| DB | 用途 | 说明 |
| --- | --- | --- |
| 0 | 业务缓存 | 商品、分类、CMS、首页聚合 |
| 1 | Celery broker | 任务队列 |
| 2 | Celery result backend | 任务结果，设置短 TTL |
| 3 | 验证码、限流计数、分布式锁 | 易失数据，禁止持久化业务数据 |

Key 命名：

```
guda:{env}:{module}:{entity}:{identifier}[:{version}]
```

示例：`guda:prod:catalog:product:1024:v3`、`guda:prod:auth:login_fail:13800001111`、`guda:prod:orders:lock:stock:sku:2001`。

| 场景 | Key 模式 | TTL | 失效策略 |
| --- | --- | --- | --- |
| 商品详情 | `catalog:product:{id}:v{n}` | 10 min | 商品/SKU 保存后版本号 +1 |
| 分类树 | `catalog:category:tree:v{n}` | 1 h | 分类变更版本号 +1 |
| 首页聚合 | `cms:home:aggregate:v{n}` | 5 min | CMS 发布/商品上下架后版本号 +1 |
| CMS 页面 | `cms:page:{slug}:v{n}` | 30 min | 发布/下线时失效 |
| 登录失败计数 | `auth:login_fail:{account}` | 15 min | 成功后清零 |
| 接口限流 | DRF throttle 默认键 | 60 s | 自动过期 |
| 库存扣减锁 | `orders:lock:stock:sku:{sku_id}` | 10 s | 事务结束释放 |
| 优惠券领取锁 | `coupons:lock:claim:{coupon_id}:{user_id}` | 10 s | 释放 |

缓存规则：缓存只存可重建数据；缓存击穿用互斥锁（`SET NX EX`）重建；缓存穿透对不存在的 ID 缓存空值 60s；批量失效采用版本号而非 `keys` 扫描（生产禁用 `KEYS`）。

### 3.7 安全架构

| 项 | 方案 |
| --- | --- |
| 传输 | 全站 HTTPS，HSTS 开启；开发环境允许 HTTP |
| 密码 | Argon2id 哈希；长度 8–64；禁止明文与弱口令字典 |
| Token | access 30 分钟、refresh 7 天；refresh 轮换 + 旧 token 进黑名单；refresh 存 `HttpOnly + Secure + SameSite=Lax` Cookie；access 仅存前端内存（Pinia），不落 localStorage |
| 鉴权 | DRF 全局 `IsAuthenticated` 默认，公开接口显式 `AllowAny`；对象级权限必须校验 `owner` |
| CSRF | Bearer Token 接口天然免疫；refresh/logout 走 Cookie 的接口校验 `Origin` 白名单 + 自定义头 `X-Requested-With` |
| 越权 | 所有按 ID 访问的资源必须带 `user` 过滤；禁止仅靠前端隐藏按钮 |
| 注入 | 全部使用 ORM / 参数化查询；禁止拼接 SQL；富文本入库前服务端白名单清洗 |
| XSS | 前端禁止 `v-html` 渲染用户内容；CMS 富文本经后端清洗后渲染；配置 CSP 基础策略 |
| 上传 | 白名单 `jpg/jpeg/png/webp`，校验 MIME 与 Pillow 解码，重命名存储，限制 5MB |
| 限流 | 匿名 60/min、登录用户 600/min、登录接口 5/min/账号、注册 3/min/IP、下单 10/min/用户 |
| 敏感数据 | 手机号 AES 加密存储 + 检索哈希列；日志与接口响应脱敏（`138****1111`） |
| 审计 | 后台写操作记录操作人、对象、前后差异、IP、UA，保留 180 天 |
| 依赖安全 | CI 执行 `pip-audit` 与 `pnpm audit`，高危漏洞阻断发布 |

## 4. 接口规范

### 4.1 基础约定

| 项 | 规定 |
| --- | --- |
| Base URL | 生产 `https://api.guda.example.com/api/v1/`；开发 `http://127.0.0.1:8000/api/v1/` |
| 版本 | 版本号置于路径 `/api/v1/`，升级为 v2 时新旧并存，旧版本保留不少于 6 个月 |
| 协议 | HTTP/1.1、HTTPS；请求与响应均为 `application/json; charset=utf-8` |
| 字段命名 | 全链路 `snake_case`，前端不得在 DTO 层改写字段名 |
| 时间格式 | ISO 8601 带时区：`2026-11-04T10:30:00+08:00` |
| 金额格式 | 字符串，两位小数：`"129.00"`；禁止返回浮点数 |
| ID | 路径参数使用对外 `public_id`（UUID v4 去横线，32 位）；内部自增 ID 不对外暴露 |
| 空值 | 统一 `null`，不使用 `""` 或 `0` 表达"无" |
| 枚举 | 大写短码，如 `"PAID"`、`"SHIPPED"`，配套 `*_label` 展示文案 |
| 字符集 | 数据库 `utf8mb4`，接口接受中文与 emoji |

### 4.2 URL 与方法语义

URL 规则：`/api/v1/{资源复数}/`，资源名使用小写字母 + 连字符；子资源用嵌套路径，层级不超过两级。

| 方法 | 语义 | 幂等 | 成功状态码 |
| --- | --- | --- | --- |
| GET | 查询（列表或详情） | 是 | 200 |
| POST | 创建 / 动作 | 否（下单用幂等键） | 201（创建）/ 200（动作） |
| PUT | 全量更新 | 是 | 200 |
| PATCH | 局部更新 | 是 | 200 |
| DELETE | 删除（软删除） | 是 | 204 |

非 CRUD 动作采用动词子路径：`POST /orders/{id}/cancel/`、`POST /orders/{id}/confirm/`、`POST /coupons/{id}/claim/`、`POST /payments/{id}/mock-pay/`。

### 4.3 统一响应体

成功响应直接返回业务数据（DRF 默认），列表统一分页结构：

```json
{
  "count": 128,
  "page": 1,
  "page_size": 20,
  "total_pages": 7,
  "next": "https://api.guda.example.com/api/v1/products/?page=2",
  "previous": null,
  "results": []
}
```

错误响应统一封装：

```json
{
  "code": "CART_STOCK_NOT_ENOUGH",
  "message": "库存不足",
  "detail": {"sku_public_id": "a1b2c3", "available": 2},
  "request_id": "req-8f1c2b9a",
  "timestamp": "2026-11-04T10:30:00+08:00"
}
```

约定：`code` 为大写下划线业务码（全局唯一）；`message` 面向人，可展示；`detail` 为结构化补充（可空）；校验错误统一 `HTTP 400 + code=VALIDATION_ERROR`，`detail.fields` 为字段级错误映射。所有响应头包含 `X-Request-ID`。

### 4.4 HTTP 状态码与业务码

| HTTP | 使用场景 |
| --- | --- |
| 200 | 查询/动作成功 |
| 201 | 资源创建成功 |
| 204 | 删除成功 |
| 400 | 参数校验失败、业务规则拒绝 |
| 401 | 未认证、Token 失效 |
| 403 | 已认证但无权限 |
| 404 | 资源不存在或无权可见 |
| 409 | 状态冲突（重复支付、重复评价、并发下单冲突） |
| 422 | 语义正确但业务不可执行（如库存不足、券不可用） |
| 429 | 触发限流 |
| 500 | 服务内部错误（不得暴露堆栈） |
| 503 | 依赖不可用（DB/Redis 探活失败） |

业务码前缀规范：`AUTH_`、`USER_`、`PRODUCT_`、`CART_`、`ORDER_`、`PAYMENT_`、`COUPON_`、`REVIEW_`、`NOTIFY_`、`CMS_`、`SUPPORT_`、`COMMON_`。完整错误码见附录 A。

### 4.5 分页 / 过滤 / 排序 / 搜索

| 参数 | 规则 |
| --- | --- |
| `page` | 从 1 开始，默认 1 |
| `page_size` | 默认 20，最大 100，超出按 100 处理 |
| 过滤 | 直接使用字段名，如 `?status=PAID&category=12`；范围用 `price_min` / `price_max` |
| 排序 | `?ordering=price,-created_at`，`-` 表示降序；白名单字段外忽略 |
| 搜索 | `?search=关键词`，仅对白名单字段生效（商品名、SKU 编码、订单号） |
| 时间范围 | `?created_from=&created_to=`，闭开区间 `[from, to)` |

### 4.6 幂等与并发

1. 下单接口必须携带 `Idempotency-Key`（UUID），服务端在 Redis 记录 `key → 订单号`，TTL 24h；重复请求返回同一订单。
2. 模拟支付回调必须携带 `payment_no` 与 `signature`（HMAC-SHA256，密钥来自环境变量），校验失败返回 401；回调按 `payment_no` 幂等，重复回调返回 200 且不重复改单。
3. 库存扣减使用 `SELECT ... FOR UPDATE` + Redis 锁双保险；超卖为 P0 缺陷。
4. 优惠券核销在订单事务内完成，禁止先核销后建单。

## 5. 命名规范

### 5.1 通用原则

1. 一个概念只用一个名字，禁止中英混用、同义词轮换（如 `user` / `member` / `customer` 混用）。
2. 命名以"业务含义"优先，禁止 `data`、`info`、`temp`、`flag`、`list2` 之类无信息量名称。
3. 布尔值用 `is_` / `has_` / `can_` 前缀；时间点用 `_at` 后缀；时长用 `_seconds`；数量用 `_count`；金额用 `_amount`（整数分）或 `_price`（Decimal）。
4. 缩写仅允许 `id`、`sku`、`spu`、`url`、`api`、`ip`、`html`，其余一律完整拼写。

### 5.2 后端（Python / Django）

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 包 / 模块 | 小写 + 下划线 | `notifications`、`order_service` |
| 类 | PascalCase | `OrderService`、`CouponValidator` |
| 函数 / 变量 | snake_case | `calculate_order_amount` |
| 常量 | 全大写 | `ORDER_TIMEOUT_MINUTES` |
| 私有成员 | 单下划线前缀 | `_apply_coupon` |
| Django app | 单数、小写 | `accounts`、`catalog`、`support` |

## 6. 字段规范

### 6.1 数据类型基线

| 业务类型 | 数据库 | API | 前端 | 说明 |

| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 不暴露 | — | 内部关联 |

| 金额 | `DECIMAL(12,2)` | `string` | `string` | 禁止 float；最小单位 0.01 |
| 数量 | `INT UNSIGNED` | `number` | `number` | 库存、件数 |
| 比例/折扣 | `DECIMAL(5,2)` | `string` | `string` | 如 `"0.85"` 表示 85 折 |
| 布尔 | `TINYINT(1)` | `boolean` | `boolean` | 字段名带 `is_` |

### 6.2 字段长度与校验标准

| 字段 | 长度 | 校验规则 |
| --- | --- | --- |
| 用户名 | 3–20 | 字母开头，字母/数字/下划线，全站唯一，不区分大小写 |
| 邮箱 | ≤ 254 | RFC 5322 简化校验，全站唯一，存储小写 |
| 手机号 | 11 | 中国大陆手机号正则 `^1[3-9]\d{9}$`，唯一 |
| 密码 | 8–64 | 至少含字母与数字；前后端同时校验 |
| 昵称 | 1–30 | 允许中文、字母、数字、下划线，敏感词过滤 |
| 收货人 | 2–20 | 中文/字母/空格 |
| 地址 | ≤ 200 | 省市区三级必填 + 详细地址 |
| 商品名称 | 2–120 | 必填，唯一性由运营保证（不强制唯一索引） |
| SKU 规格 | ≤ 60 | 如"红色 / L" |
| SKU 编码 | 8–32 | 大写字母 + 数字 + 连字符，全站唯一 |
| 订单号 | 20 | 规则 `GD + yyyyMMddHHmmss + 4 位随机`，全局唯一 |
| 支付单号 | 24 | `PAY + 订单号后 17 位 + 4 位序号` |
| 评价内容 | 5–500 | 纯文本，敏感词过滤 |
| 客服消息 | 1–1000 | 纯文本，禁止 HTML |
| CMS 富文本 | ≤ 20000 | 服务端白名单清洗后入库 |
| 图片 | ≤ 5 MB | `jpg/jpeg/png/webp`，宽高 ≤ 4096px |

### 6.3 金额与优惠计算规范

1. 所有金额以 `Decimal` 计算，统一 `ROUND_HALF_UP` 保留两位；禁止在任何环节转 `float`。
2. 计算顺序固定：商品小计 → 优惠券抵扣 → 运费 → 应付金额。运费规则：实付满 99 元免运费，否则 10 元；免邮券优先抵消运费。
3. 优惠券抵扣后金额不得为负，最小为 0.01 元；差额不找零、不退现。
4. 订单金额快照必须落库：`items_amount`、`discount_amount`、`shipping_amount`、`payable_amount`，均为 `DECIMAL(12,2)`。
5. 任何金额变动必须写入 `order_amount_logs`（订单号、变更前后、原因、操作人）。

### 6.4 通用字段与审计字段

所有业务表必须包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BigAutoField | 主键 |
| `public_id` | Char(32) unique | 对外标识，创建时生成，不可变 |
| `created_at` | DateTime | 自动写入 |
| `updated_at` | DateTime | 自动更新 |
| `is_deleted` | Boolean default False | 软删除标记 |
| `deleted_at` | DateTime null | 删除时间 |

需审计的表额外包含 `created_by`、`updated_by`（外键 `accounts.User`，`null=True`）。订单、支付、优惠券核销、库存变更表禁止物理删除与批量更新绕过 service。

### 6.5 敏感字段与脱敏

| 字段 | 存储 | 展示 | 日志 |
| --- | --- | --- | --- |
| 手机号 | AES-256-GCM 密文 + `phone_hash`（SHA-256）用于唯一与检索 | `138****1111` | 禁止输出 |
| 密码 | Argon2id 哈希 | 不展示 | 禁止输出 |
| 收货地址 | 明文（仅本人与订单相关角色可见） | 本人可见完整，客服仅见省市 | 脱敏 |
| 支付签名 | 不落库 | 不展示 | 禁止输出 |
| 身份证 / 银行卡 | 本期不采集 | — | — |

### 6.6 字段设计禁令

1. 禁止使用 `NULL` 表示业务默认值（用 `default` 明确表达）；仅在"确实无值"时用 `null=True`。
2. 禁止用逗号分隔字符串存多值（如 `images="a.jpg,b.jpg"`），使用关联表或 JSON 数组。
3. 禁止在同一字段混存多种语义（如 `remark` 同时存客服备注与系统原因）。
4. 禁止省略外键约束（`db_constraint=True`），禁止跨库伪外键。
5. 禁止使用 `FloatField` 存金额或比例。
6. 禁止给大文本字段建普通索引；搜索使用前缀索引或独立检索方案。

### 7.4 数据一致性规则

1. 订单、支付、库存、优惠券四类数据的所有写操作必须经过对应 `services` 层，禁止在视图、信号、管理后台直接 `save()` 改状态。
2. 订单状态机与支付状态机的流转必须校验前置状态，非法流转抛 `OrderStatusConflict`（HTTP 409）。
3. 冗余字段（商品 `price_min`/`price_max`/`sales_count`、券 `claimed_quantity`）由 service 在同一事务内维护，并提供每日校验脚本（`manage.py check_data_consistency`）。
4. 所有金额、状态变更记录流水表，流水表只追加不修改。
5. 数据库事务隔离级别使用默认 `REPEATABLE READ`；库存扣减必须显式行锁，不使用乐观锁重试以外的补偿逻辑。

## 8. 技术要求

### 8.1 后端开发要求

| 项 | 要求 |
| --- | --- |
| Python 版本 | 3.12（生产与开发一致，禁止版本漂移） |
| 配置管理 | `django-environ` 读取 `.env`；`base/dev/prod` 三层；生产 `DEBUG=False`、`ALLOWED_HOSTS` 白名单、`SECRET_KEY` 必填 |
| 模型 | 继承 `common.models.BaseModel`（统一 `public_id`、审计与软删除字段）；`Meta.db_table` 显式声明表名 |
| 序列化器 | 读写分离：`XxxWriteSerializer` 负责校验，`XxxReadSerializer` 负责展示；禁止一个序列化器同时承担写与复杂读 |
| 视图 | 优先 `APIView`/`GenericAPIView` + 显式 service 调用；禁止在视图内写 `for` 循环处理业务 |
| 权限 | 全局默认 `IsAuthenticated`；公开接口显式 `AllowAny`；对象级权限在 `permissions.py` 实现并单测 |
| 事务 | 写操作必须 `transaction.atomic()`；事务内禁止发消息、发邮件、调外部接口；副作用使用 `transaction.on_commit` |
| 查询 | 列表接口必须 `select_related`/`prefetch_related`；单次请求查询数 ≤ 8；禁止在循环内查询（N+1） |
| 分页 | 统一 `PageNumberPagination`，`page_size` 上限 100 |
| 异常 | 统一异常处理器输出 4.3 结构；业务异常继承 `common.exceptions.BusinessError`（携带 code/status/detail）；禁止 `except Exception: pass` |
| 日志 | 结构化日志；异常必须带 `request_id` 与堆栈（仅服务端落盘，不返回客户端） |
| 异步任务 | 所有耗时 > 200ms 的副作用（通知、图片处理、券到期提醒）走 Celery；任务必须幂等、可重试、设置 `max_retries` |
| 定时任务 | Celery Beat：每分钟扫描超时订单、每日清理过期券、每日校验数据一致性 |
| 迁移 | 每次模型变更必须附带迁移文件；禁止在迁移中写业务数据加工逻辑；生产迁移前必须备份 |
| 管理后台 | 仅作应急运维手段，不承载运营日常流程；后台操作必须写审计日志 |
| 单元测试 | 新增 service 必须有测试；修改缺陷必须先补回归测试 |
| 依赖 | 锁定 `uv.lock`；新增依赖需在评审中说明用途，禁止引入与现有能力重复的库 |

关键实现约束：

1. 库存扣减伪代码（唯一允许的写法）：

```python
with transaction.atomic():
    sku = Sku.objects.select_for_update().get(id=sku_id)
    if sku.stock < quantity:
        raise BusinessError("CART_STOCK_NOT_ENOUGH", status=422)
    sku.stock = F("stock") - quantity
    sku.locked_stock = F("locked_stock") + quantity
    sku.save(update_fields=["stock", "locked_stock", "updated_at"])
    StockLog.objects.create(...)
```

2. 订单创建、支付成功、取消订单的库存处理必须成对出现：`lock → deduct`、`unlock → restore`，并在同一 service 文件中实现。
3. 所有对外 `public_id` 由 `BaseModel.save()` 首次保存时生成，禁止在序列化层临时生成。
4. 所有接口返回的当前用户相关资源必须带 `user` 过滤，禁止依赖前端传参。

## 10. 基本功能与业务规则

### 10.1 注册 / 登录

| 场景 | 规则 |
| --- | --- |
| 注册方式 | 邮箱注册（必填邮箱 + 用户名 + 密码）；手机号注册需先完成邮箱验证后在个人中心绑定 |
| 验证码 | 6 位数字，有效期 5 分钟，同一邮箱 60 秒内不可重发，每日最多 10 次 |
| 注册校验 | 邮箱/用户名唯一（不区分大小写）；密码 8–64 位含字母与数字；敏感词过滤 |
| 登录 | 支持用户名或邮箱 + 密码；连续失败 5 次锁定 15 分钟（Redis 计数） |
| 令牌 | access 30 分钟；refresh 7 天，每次刷新轮换并作废旧 refresh |
| 登出 | refresh 加入黑名单并清 Cookie；access 由前端立即丢弃 |
| 找回密码 | 发送一次性链接（有效期 30 分钟，仅可使用一次）；重置后所有 refresh 失效 |
| 账号状态 | `is_active=False` 的账号登录返回 403，提示联系客服 |

### 10.2 商品展示

1. 分类为两级树（一级 + 二级），商品必须挂在二级分类；分类删除前置校验：存在商品则禁止删除。
2. 前台仅展示 `ON_SALE` 商品与 SKU；`OFF_SALE`、`DRAFT` 商品详情返回 404（不返回 403，避免暴露存在性）。
3. 商品详情展示：主图/图集、名称、副标题、SKU 规格选择、价格区间、库存状态（"现货/仅剩 N 件/缺货"）、销量、评价聚合、详情富文本、相关推荐。
4. 库存展示阈值：`stock <= 5` 显示"仅剩 N 件"；`stock = 0` 显示"缺货"且禁止加购。
5. 列表排序支持：综合（默认，销量 + 权重）、价格升/降、销量降、最新上架；排序字段白名单。
6. 搜索：按名称前缀/包含匹配，禁止全文模糊扫描大表；搜索词长度 1–30，超出截断。
7. 价格展示以 SKU 最低价为列表价，详情页按所选 SKU 展示实际售价。

### 10.3 购物车

1. 本期购物车仅登录可用；未登录点击加购跳转登录并保留目标商品（登录后引导重新加购）。
2. 单个用户购物车最多 50 个 SKU 项，单项数量 1–99。
3. 加购校验：SKU 必须上架、`stock > 0`、加购后数量不超过可用库存。
4. 读取购物车时实时校验状态：下架商品标记 `INVALID`、库存不足标记 `INSUFFICIENT`，不计入可结算项。
5. 结算只取 `is_selected=True` 的有效项；无有效项禁止进入结算。
6. 金额试算：`items_amount = Σ(单价 × 数量)`；运费与优惠在结算预览中计算，购物车页只展示商品小计。
7. 下单成功后，已结算项从购物车移除；下单失败不清空。

### 10.4 订单系统

订单状态与流转：

```
                 ┌──────────────┐
   下单成功 ───▶ │ PENDING_PAYMENT │ ──支付成功──▶ PAID ──发货──▶ SHIPPED ──确认收货──▶ COMPLETED
                 └──────┬───────┘                │                  │
                        │ 用户取消/30 分钟超时     │ 发起退款          │ 售后申请
                        ▼                        ▼                  ▼
                   CANCELLED              REFUNDING ──退款完成──▶ REFUNDED
```

| 状态 | 含义 | 允许操作 |
| --- | --- | --- |
| `PENDING_PAYMENT` | 待支付 | 支付、取消 |
| `PAID` | 已支付/待发货 | 后台发货、后台发起退款 |
| `SHIPPED` | 已发货/待收货 | 确认收货、售后申请 |
| `COMPLETED` | 已完成 | 评价、售后申请（完成后 7 天内） |
| `CANCELLED` | 已取消 | 仅查看 |
| `REFUNDING` | 退款中 | 仅查看 |
| `REFUNDED` | 已退款 | 仅查看 |

业务规则：

1. 下单必须基于结算预览：重新校验地址、SKU 状态、库存、券可用性，任一变化返回 422 并要求用户刷新结算页。
2. 下单事务内完成：创建订单 → 锁定库存 → 锁定优惠券 → 生成支付单（`PENDING`）→ 清空已结算购物车项。
3. 支付超时 30 分钟：Celery Beat 每分钟扫描，自动取消并释放库存、退还优惠券。
4. 取消：仅 `PENDING_PAYMENT` 可由用户取消；`PAID` 之后只能走退款流程（本期仅状态流转，无资金操作）。
5. 发货：运营填写运单号后状态变 `SHIPPED`，同时写入 `shipped_at` 并产生站内消息。
6. 确认收货：用户点击确认或发货后 15 天自动确认（定时任务），状态变 `COMPLETED`，同时累加商品销量。
7. 已完成订单 7 天内可申请售后，进入 `REFUNDING`；退款完成由运营标记 `REFUNDED`。
8. 订单列表默认按创建时间倒序，支持状态筛选与订单号精确搜索。
9. 订单取消/退款成功后必须恢复库存与优惠券，操作必须幂等（重复触发不重复恢复）。

### 10.5 支付（流程演示）

1. 支付方式全部为模拟渠道，页面明确标注"演示支付，不会产生真实扣款"。
2. 支付流程：订单详情 → 选择渠道 → 生成/复用支付单 → 跳转模拟收银台 → 点击"支付成功/支付失败" → 前端调用回调模拟接口 → 后端校验签名与金额 → 更新支付单与订单。
3. 支付单金额必须等于订单 `payable_amount`，不一致返回 422 并记录异常日志。
4. 回调校验：`payment_no` 存在且状态 `PENDING`、金额一致、签名正确；任一不满足返回 401/422。
5. 回调幂等：已 `SUCCESS` 的支付单再次回调直接返回 200，不重复更新订单、不重复加销量、不重复发消息。
6. 支付成功后在 `transaction.on_commit` 中：订单转 `PAID`、优惠券转 `USED`、锁定库存转已扣减、生成 `ORDER_PAID` 消息、累加销量。
7. 支付失败：支付单 `FAILED`，订单保持 `PENDING_PAYMENT`，用户可重新发起支付（复用同一订单，新建支付单须关闭旧单）。
8. 订单取消或超时后，支付单统一置 `CLOSED`，禁止再支付。

### 10.6 优惠券

| 类型 | 计算 | 约束 |
| --- | --- | --- |
| `FIXED` 满减 | `discount = min(value, eligible_amount)` | `eligible_amount >= min_amount` |
| `DISCOUNT` 折扣 | `discount = eligible_amount × (1 - value)`，四舍五入两位；超过封顶取封顶值 | `value` 取 `0.01–0.99` |
| `FREE_SHIPPING` 免邮 | 运费置 0 | 仅抵扣运费，不影响商品金额 |

规则：

1. 一期一张订单只能使用一张券，不支持叠加；券与"限时折扣"等其它促销不叠加（本期无其它促销）。
2. 适用范围 `ALL` / `CATEGORY` / `PRODUCT`：`eligible_amount` 仅统计适用商品的小计。
3. 领取：校验活动状态、有效期、总量余量、每人限领；`claimed_quantity` 使用原子递增，超发即事务回滚。
4. 使用：下单事务内将券由 `UNUSED` 置 `LOCKED` 并绑定订单；支付成功置 `USED`；取消/超时置回 `UNUSED`（若已过期则置 `EXPIRED`）。
5. 券不可转赠、不可兑现、不可跨用户使用；过期券每日定时批量置 `EXPIRED`。
6. 结算页必须展示券不可用原因（门槛不足/不适用/已过期）。

### 10.7 用户评价

1. 仅 `COMPLETED` 订单可评价，且完成后 7 天内可提交；一单只能评一次（数据库唯一约束）。
2. 评分 1–5 星必填，内容 5–500 字必填，图片最多 3 张（可选）。
3. 提交后状态 `PENDING`，运营审核；`APPROVED` 才前台展示，`REJECTED` 需填写原因并通知用户。
4. 支持匿名展示（隐藏用户名，保留头像脱敏）；敏感词命中直接进入人工审核。
5. 商品详情展示评价聚合（平均分、评价数、各星级占比）与最新 10 条评价，分页查看更多。
6. 评价不可修改；审核驳回后允许用户重新提交（覆盖原记录，状态回到 `PENDING`）。

### 10.8 用户通知

1. 触发事件：支付成功、发货、订单取消（含超时取消）、退款完成、优惠券即将到期（前 3 天）、评价审核结果、客服回复、系统公告。
2. 消息字段见 7.3；消息体不包含完整手机号、地址等敏感信息。
3. 未读数由 `is_read=False` 统计；前端每 30 秒轮询未读数，消息页进入时拉取列表。
4. 标记已读幂等；全部已读一次事务完成；消息保留 12 个月，之后归档清理。
5. 消息生成统一在 `notifications.services.create_notification()` 内完成，业务模块不得直接插表。

### 10.9 CMS

1. 内容模型：栏目（Section）→ 页面（Page）；轮播位（Banner）与公告（Announcement）独立管理。
2. 页面状态：`DRAFT` → `PUBLISHED` → `OFFLINE`；只有 `PUBLISHED` 且当前时间在展示窗口内才对外可见。
3. 富文本由运营在后台录入，服务端使用白名单清洗（允许标签：`p/br/strong/em/ul/ol/li/h2/h3/img/a/table`，禁止 `script/style/iframe` 与事件属性）。
4. 图片统一上传至 media，正文内图片使用相对路径或 CDN 前缀，禁止外链任意域名。
5. 发布/下线/排序变更后必须使对应缓存版本号 +1，保证 5 分钟内前台生效（实际为即时失效）。
6. 首页聚合内容（轮播 + 公告 + 推荐商品）由 `cms.selectors` 组装，缓存 5 分钟。

### 10.10 用户中心

1. 个人信息：昵称、头像、性别（可选）、生日（可选）；邮箱/手机号修改需验证码校验。
2. 修改密码：需校验原密码，成功后所有 refresh 失效并要求重新登录。
3. 地址管理：最多 20 条；默认地址唯一（设置新的默认自动取消旧的）；被未完成订单引用的地址只能软删除。
4. 交易记录：按订单状态分组展示，含商品快照、金额、物流单号、操作按钮；数据与订单详情一致。
5. 我的优惠券：按 `UNUSED / USED / EXPIRED` 分组，展示使用门槛、有效期、适用范围。
6. 账号注销：本期不开放自助注销，需联系客服处理（软删除 + 匿名化）。

### 10.11 客服系统

1. 会话生命周期：`WAITING`（用户发起）→ `ACTIVE`（客服接管）→ `CLOSED`（客服关闭或 24 小时无消息自动关闭）。
2. 用户同一时间只能有一个未关闭会话；可关联订单，客服可查看该订单只读信息。
3. 消息按 `created_at` 升序，前端 5 秒轮询增量拉取（`after=<最后一条消息时间或 ID>`），不做 WebSocket。
4. 发送校验：会话未关闭、发送者为会话参与者（用户本人或已接管客服）；客服未接管时只能查看不可回复。
5. 消息为纯文本，禁止 HTML；命中敏感词时提示并记录；消息保留 12 个月。
6. 客服队列按 `last_message_at` 升序（先到先服务）；接管采用乐观锁，避免多人同时接管。
7. 关闭会话后双方只读，用户可新建会话继续咨询。
