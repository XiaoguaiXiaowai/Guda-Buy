## 8. 必须沿用的约定

1. 所有购物车写操作只进 `apps/cart/services.py`，视图只做协议转换；读与金额试算只进 `selectors.py`。
2. 同一用户同一 SKU 只保留一行；加购必须合并数量，禁止直接 `create` 绕过服务层。
3. 并发安全顺序固定为 **先锁 SKU 行、再锁购物车项行**；唯一约束是兜底，不得依赖 `IntegrityError` 做常规流程。
4. 加购/改数量必须同时校验商品与 SKU 上架状态、库存；失效原因优先级：商品删除 → 商品下架 → 规格下架 → 库存不足。
5. 金额一律用 `Decimal` 计算并输出两位小数字符串；禁止浮点运算，禁止返回数字类型金额。
6. 可结算金额只统计 `status=VALID` 且 `is_selected=true` 的项；失效/库存不足项仍展示但不计数。
7. 数量为 0 的 PATCH 等同删除并返回 204；删除为硬删除，重复删除返回 404，不得返回 500。
8. 上限读取 `settings.CART_MAX_ITEMS`（默认 50）与 `settings.CART_ITEM_MAX_QUANTITY`（默认 99），不要在代码里硬编码。
9. 对外标识一律使用 `public_id`；跨用户操作统一返回 404，避免泄露资源是否存在。
10. 角标使用 `GET /cart/count/` 的 `total_quantity`（总件数），`count` 为商品种数；未登录或接口失败时清零。
11. 购物车失效判定是**读取时实时计算**，不要在商品下架时批量改购物车数据。

## 9. I4 已知坑

| 现象 | 处理 |
| --- | --- |
| 加购返回 422 `CART_ITEM_INVALID` | 商品或 SKU 已下架/删除；先确认 `product.status` 与 `sku.status` 均为 `ON_SALE` |
| 加购返回 422 `CART_STOCK_NOT_ENOUGH` | `detail.available` 是当前可用库存；合并后的数量也会校验，不只是本次数量 |
| 第 51 个 SKU 加购失败 | 上限是「商品种数」50，不是件数；同 SKU 合并数量不受此项限制 |
| 数量改到 100 被 400 | 单项上限 99，由序列化器拦截；合并后超 99 由服务层返回 422 `CART_ITEM_LIMIT` |
| 重复删除第二次返回 404 | 属预期，保证不 500；前端删除后应重新拉取列表 |
| 角标显示 2 但列表只有 1 行 | 角标是总件数，行数是商品种数；两者都来自 `/cart/count/` |
| 后台下架后购物车金额没变 | 刷新 `/cart/` 重新计算；失效判定不落库 |
| 未登录点加购没有报 401 | 前端先跳登录并带 `redirect`，登录后回到原详情页 |
| browser_use 子代理报 viewport 未就绪 | 本机该子代理环境异常，改用 Playwright MCP（headless）复测，不影响应用本身 |
| 前端整页刷新后短暂显示未登录 | 访问令牌仅存内存，刷新时依赖 HttpOnly refresh cookie 恢复；等待恢复完成再判断，不要据此改登录态持久化 |

1. **提交 I4 改动**：当前分支 `I4` 工作区含全部 I4 代码与文档，建议先 commit，再切 I5 分支。
2. **启动 I5 订单系统**：结算预览直接复用 `GET /cart/` 的 `summary.items_amount` 与勾选项，不要在前端重算金额。
3. **下单入参**：以购物车项 `public_id` 列表 + 地址 `public_id` + 幂等键提交；服务端重新校验库存与上架状态，不能信任前端金额。
4. **库存锁定**：沿用「按 SKU 行加锁」的模式，I5 多 SKU 下单需**按 SKU id 升序加锁**，避免与 I4 加购交叉死锁。
5. **清空时机**：下单成功后只删除本次下单的购物车项，不能直接 `clear_cart` 清空全部。
6. **I5 地址约束**：删除被未完成订单引用地址时返回 422（I1-2），在订单模型落地后一并补齐。
7. **I0-3**：主包 984 kB，I5 新增页面较多，建议在 I5 前完成 Element Plus 按需引入或 manualChunks。
