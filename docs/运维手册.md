# Guda 商城运维手册（I11 上线加固）

本手册面向值班运维与后端负责人，覆盖日常巡检、发布回滚、备份恢复、监控告警和常见故障处置。
部署拓扑、目录与脚本以仓库内 `deploy/`、`backend/scripts/` 为准。

---

## 1. 服务拓扑

| 组件 | 部署方式 | 入口 / 关键路径 |
| --- | --- | --- |
| Nginx | systemd（发行版自带） | `443` → `unix:/srv/guda/run/gunicorn.sock`，静态文件根 `/srv/guda/frontend` |
| Django API | `guda-web.service`（Gunicorn） | `config.wsgi:application`，workers = `max(3, CPU*2+1)`，超时 60s |
| Celery Worker | `guda-celery.service` | 订单超时取消、通知、客服自动关闭等异步任务 |
| Celery Beat | `guda-celerybeat.service` | 定时调度（每分钟订单超时、每小时客服关闭等） |
| MariaDB | 本机服务 | 仅监听 `127.0.0.1:3306`，禁止公网暴露 |
| Redis | 本机服务 | 仅监听 `127.0.0.1:6379`，db0 缓存 / db1 队列 / db2 结果 |

生产目录：

```
/srv/guda/app       代码（Git 仓库，发布脚本在此执行）
/srv/guda/frontend  前端 dist 产物（rsync 覆盖）
/srv/guda/media     用户上传文件
/srv/guda/static    collectstatic 产物
/srv/guda/logs      app.log / error.log / gunicorn / celery
/srv/guda/backups   数据库与媒体备份
/srv/guda/env/.env  生产环境变量（600，属主 guda）
/srv/guda/.last_release  回滚点（发布前提交号）
```

## 2. 日常巡检

| 频率 | 检查项 | 命令 / 判定 |
| --- | --- | --- |
| 每 30 秒（自动） | 外部探活 | `PROBE_URL=https://guda.example.com/healthz/ deploy/scripts/health-probe.sh`，退出码 0 |
| 每日 | 服务状态 | `systemctl is-active guda-web guda-celery guda-celerybeat nginx mariadb redis-server` |
| 每日 | 磁盘 | `df -h /srv`，使用率 < 80% |
| 每日 | 备份 | 确认 `/srv/guda/backups/db-<日期>.sql.gz` 存在且 `gzip -t` 通过 |
| 每周 | 错误日志 | `error.log` 无持续增长；5xx 占比 < 1% |
| 每周 | 队列 | Celery 队列无持续积压，定时任务按点执行 |
| 每月 | 恢复演练 | 备份恢复到临时库并核对订单数与金额（见第 4 节） |
| 每季度 | 证书 | `openssl s_client -connect guda.example.com:443 -servername guda.example.com </dev/null 2>/dev/null \| openssl x509 -noout -dates` |

日志轮转由 `deploy/logrotate/guda` 负责：每日轮转、保留 14 天、压缩。

## 3. 发布与回滚（15 分钟窗口）

### 3.1 发布前检查单

1. 发布窗口内无大促/对账任务，通知相关方。
2. 代码已合入并打 tag，CI 门禁全绿（pytest / vitest / type-check / lint / build / E2E）。
3. 变更含数据库迁移时，先执行备份：
   `ENV_FILE=/srv/guda/env/.env BACKUP_DIR=/srv/guda/backups bash backend/scripts/backup.sh`
4. 记录当前版本：`git -C /srv/guda/app rev-parse --short HEAD`。

### 3.2 发布

```bash
cd /srv/guda/app
bash backend/scripts/publish.sh
```

脚本依次执行：记录回滚点 → 拉取 `origin/main` → 安装依赖 → `migrate` → `collectstatic`
→ `pnpm build` → 同步 dist → 重启三个 systemd 服务 → 冒烟（失败重试 3 次）。

发布后人工确认：

1. `curl -fsS https://guda.example.com/healthz/` 返回 `{"status":"ok","db":"ok","redis":"ok"}`。
2. `SMOKE_BASE_URL=https://guda.example.com bash backend/scripts/smoke.sh` 通过 5 项。
3. 抽查首页、商品详情、加购、下单、支付回调各 1 次。
4. `error.log` 无新增 5xx 堆栈。

### 3.3 回滚

冒烟失败或发布后 5xx 激增时立即回滚：

```bash
cd /srv/guda/app
bash backend/scripts/rollback.sh
```

回滚点来自 `/srv/guda/.last_release`；回滚后重新构建前端、重启服务并再次冒烟。
数据库迁移回滚须按迁移文件中的 `reverse` 方案人工确认，禁止直接 `migrate zero`。

### 3.4 发布/回滚演练记录（本机模拟）

| 步骤 | 命令 | 结果 | 耗时 |
| --- | --- | --- | --- |
| 迁移前备份 | `backend/scripts/backup.sh` | db + media 备份成功 | 0.7s |
| 数据库迁移 | `migrate --noinput` | `No migrations to apply` | 2.2s |
| 发布构建 | `pnpm build` | 69 个产物，`built in 4.66s` | 10.3s |
| 发布后冒烟 | `smoke.sh`（public） | 6 项通过、0 失败 | 2.2s |
| 回滚 | 恢复上一版 `dist` | `index.html` 哈希回到 `dc11cc31…` | 0.1s |
| 回滚后冒烟 | `smoke.sh`（public） | 6 项通过、0 失败 | 1.6s |

两次演练合计均在 1 分钟内完成，远低于 15 分钟上限；`/healthz` 全程 200。

## 4. 备份与恢复

### 4.1 备份

生产建议 cron 每日 03:00 执行：

```cron
0 3 * * * ENV_FILE=/srv/guda/env/.env /srv/guda/app/backend/scripts/backup.sh >> /srv/guda/logs/backup.log 2>&1
```

产物：`db-<时间戳>-<commit>.sql.gz`、`media-<时间戳>-<commit>.tar.gz`，默认保留 30 天。
备份后校验：`gzip -t /srv/guda/backups/db-*.sql.gz`。

### 4.2 恢复

```bash
# 恢复到临时库（禁止直接覆盖生产库验证）
FORCE=1 ENV_FILE=/tmp/restore.env bash backend/scripts/restore.sh db /srv/guda/backups/db-xxx.sql.gz
FORCE=1 ENV_FILE=/tmp/restore.env bash backend/scripts/restore.sh media /srv/guda/backups/media-xxx.tar.gz
```

`restore.env` 从生产 `.env` 复制后仅修改 `DB_NAME` 为临时库名。

### 4.3 数据核对 SQL

```sql
SELECT COUNT(*) AS orders,
       COALESCE(SUM(payable_amount), 0) AS payable_sum,
       COALESCE(SUM(items_amount), 0)   AS items_sum,
       COALESCE(SUM(discount_amount), 0) AS discount_sum
FROM orders_orders;
```

## 5. 监控与告警

### 5.1 探活

- 应用层：`GET /healthz/`，校验 DB 与 Redis，任一异常返回 503，并带 `request_id`。
- 外部探活：`deploy/scripts/health-probe.sh`，可挂 systemd timer / 云拨测 / blackbox_exporter。
- Prometheus blackbox 目标：`https://guda.example.com/healthz/`，job 名 `guda-healthz`。

本地验证：

```
PROBE_URL=http://127.0.0.1:8000/healthz/  → exit 0（db=ok redis=ok）
PROBE_URL=http://127.0.0.1:9/healthz/     → exit 1（连接失败）
PROBE_URL=http://127.0.0.1:8000/api/v1/cart/ → exit 1（401，字段缺失）
```

### 5.2 告警规则

规则文件：`deploy/prometheus/guda-alerts.yml`（3 组 9 条）。

| 告警 | 触发条件 | 级别 | 处置 |
| --- | --- | --- | --- |
| GudaProbeMissing | 5 分钟无探活指标 | critical | 检查 blackbox / Prometheus 抓取 |
| GudaHealthzProbeFailed | `probe_success==0` 持续 1 分钟 | critical | 服务进程或网络，见 7.1/7.2 |
| GudaHealthzDependencyFailed | healthz 返回 503 持续 1 分钟 | critical | 按 `detail.db/redis` 定位依赖 |
| GudaMysqlDown | `mysql_up==0` | critical | 见 7.1 |
| GudaRedisDown | `redis_up==0` | critical | 见 7.2 |
| GudaDiskUsageHigh | 磁盘 > 80% 持续 10 分钟 | warning | 清理日志/备份或扩容 |
| GudaDiskUsageCritical | 磁盘 > 90% 持续 5 分钟 | critical | 立即清理，见 7.4 |
| GudaHttp5xxRateHigh | 5xx 占比 > 1% 持续 5 分钟 | critical | 见 7.3，必要时回滚 |
| GudaHttp5xxBurst | 5 分钟 5xx > 50 次 | warning | 见 7.3 |

送达要求：Alertmanager `group_wait=30s`、`group_interval=1m`、`repeat_interval=4h`，
critical 走电话/IM，warning 走群消息，确保 5 分钟内触达。

### 5.3 依赖的采集组件

`blackbox_exporter`（探活）、`node_exporter`（磁盘）、`mysqld_exporter`、`redis_exporter`、
`nginx-prometheus-exporter`（5xx 计数）。生产接入后需按实际 job 名调整规则标签。

> 说明：本机未部署 Prometheus/Alertmanager，规则已通过 YAML 语法校验（3 组 9 条），
> 真实告警触达需在生产环境联调确认；“停止 Redis / 制造 500”属破坏性操作，未在本机执行。

## 6. 日志与 request_id 定位

| 日志 | 路径 | 说明 |
| --- | --- | --- |
| 应用访问 | `/srv/guda/logs/app.log` | JSON 行，含 request_id、duration_ms、result、user_id |
| 错误 | `/srv/guda/logs/error.log` | ERROR 及以上，含堆栈 |
| Nginx | `/var/log/nginx/access.log`、`error.log` | 网关层状态码与耗时 |
| Celery | `/srv/guda/logs/celery*.log` | 任务执行与重试 |

定位步骤：

1. 从响应头或错误体取 `X-Request-ID` / `request_id`。
2. 检索应用日志：
   `grep '"request_id": "req-xxxx"' /srv/guda/logs/app.log /srv/guda/logs/error.log`
3. 需要结构化过滤时：
   `jq -c 'select(.request_id=="req-xxxx")' /srv/guda/logs/app.log`
4. Nginx 侧按时间与 URI 关联，确认是网关超时还是应用返回。

本地已验证：携带 `X-Request-ID: i11-evidence-001` 请求 `/api/v1/cart/`，
`app.log` 可检索到同 id 的 401 访问记录。

## 7. 常见故障处置

### 7.1 数据库不可用（healthz `db=fail` / `mysql_up=0`）

1. `systemctl status mariadb`，确认进程与端口 `ss -lntp | grep 3306`。
2. 查看 `/var/log/mysql/error.log`：磁盘满、连接数上限、表损坏。
3. `df -h /srv`，空间不足先清理（见 7.4）。
4. 连接数：`SHOW PROCESSLIST;` 排查长事务与连接泄漏。
5. 恢复后访问 `/healthz/` 确认 200；必要时重启 `guda-web` 释放失效连接。

### 7.2 Redis 不可用（healthz `redis=fail` / `redis_up=0`）

1. `systemctl status redis-server`、`redis-cli ping`。
2. 缓存类接口应降级直查 DB；若出现整体 5xx，检查应用是否误把缓存当唯一数据源。
3. 恢复后检查 Celery 队列积压：`celery -A config inspect active`、队列长度监控。
4. 队列积压超过阈值时，临时扩容 worker：`systemctl restart guda-celery` 后观察消费速率。

### 7.3 5xx 激增

1. 取最近一条错误响应的 `request_id`，检索 `error.log` 堆栈。
2. 按 URI 聚合 Nginx 日志，判断是否为单一接口：
   `awk '{print $7, $9}' /var/log/nginx/access.log | grep ' 5' | sort | uniq -c | sort -rn | head`
3. 若与最近发布相关且 5 分钟内无法定位，直接执行 `rollback.sh`。
4. 回滚后确认 `/healthz/` 与冒烟 5 项通过。

### 7.4 磁盘使用率告警

1. `du -sh /srv/guda/backups /srv/guda/logs /var/log` 找大头。
2. 清理超过保留期的备份与轮转日志；`logrotate -f /etc/logrotate.d/guda` 强制轮转。
3. 检查数据库 binlog 与临时文件；确认无异常大文件写入。
4. 清理后确认磁盘 < 80%，告警自动恢复。

### 7.5 支付回调失败 / 重复回调

1. 查 `error.log` 中 `signature`、`amount` 相关错误码。
2. 回调验签失败：核对 `PAYMENT_CALLBACK_SECRET` 是否与支付方一致。
3. 重复回调：依赖 `payment_no` 唯一约束与幂等逻辑，确认订单只 PAID 一次。
4. 回调缺失导致订单停留待支付：核对支付流水与订单状态，必要时人工补单并记录。

### 7.6 订单卡单 / 库存不一致

1. 待支付超时订单应由 Celery 定时取消并释放库存；检查 beat 是否运行。
2. 可用库存 = `stock - locked_stock`；异常时按订单明细核对锁定与释放记录。
3. 禁止手工改库存，先定位重复释放或未释放的订单，再按审计要求修正。

### 7.7 前端白屏 / 资源 404

1. 确认 `/srv/guda/frontend/index.html` 存在且为最新构建（对比 `dist/index.html` 哈希）。
2. 检查 Nginx `root` 与 `try_files`，确认 SPA 路由回退到 `index.html`。
3. 发布中断导致 dist 不完整时，重新 `pnpm build` 并 rsync，或回滚到上一版本。

### 7.8 Celery 任务积压

1. `celery -A config inspect active/reserved` 查看执行中任务。
2. 检查 Redis 连接与 broker 配置；确认 worker 未因异常退出。
3. 单任务异常应隔离重试，禁止清空队列丢弃业务消息。

## 8. 安全基线

1. 生产 `DEBUG=False`，`ALLOWED_HOSTS` 仅业务域名，`runserver` 禁止使用。
2. MariaDB、Redis 仅监听本机，安全组不开放 3306/6379。
3. `.env` 权限 600、属主 `guda`；密钥轮换后重启服务并观察登录态。
4. Nginx 已启用 HSTS、`X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`。
5. 日志禁止打印密码、Token、完整手机号；错误响应不返回堆栈与自增 ID。
6. 后台账号按 `admin/operator/support` 分组最小授权，离职即回收。
