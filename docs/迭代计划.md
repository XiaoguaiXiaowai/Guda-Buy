## 1. 迭代总览

### 1.1 划分原则

1. **每个迭代交付一个完整功能块**，可独立部署、独立验证、独立回滚，不依赖未交付的后续迭代。
2. 迭代内任务按"数据模型 → 服务层 → 接口 → 前端 → 测试"顺序推进，禁止跨层倒序开发。
3. 迭代出口以"部署到预发环境并通过本迭代验证清单"为准，不以"代码写完"为准。
4. 每个任务完成后必须在本文档对应迭代的《验收登记表》登记，未登记视为未完成。
5. 本文档不设时间盒；迭代顺序即依赖顺序，完成一个再进入下一个。

## 2. 迭代执行与验收机制

### 2.1 单迭代生命周期

| 阶段 | 动作 | 产出 |
| --- | --- | --- |
| 1. 进入 | 确认上游迭代已关闭、依赖接口可用 | 迭代启动记录（负责人、范围确认） |
| 2. 开发 | 按任务顺序开发，每个任务独立分支 | 代码、迁移、测试用例 |
| 3. 自测 | 执行任务验证清单中的自动化项 | 本地测试输出、覆盖率报告 |
| 4. 评审 | 代码评审，按架构文档 8.4 检查项核对 | 评审意见与修复记录 |
| 5. 部署验证 | 发布到预发环境，执行本迭代《独立部署验证场景》 | 部署记录（版本号、时间、操作人）、验证证据 |
| 6. 验收登记 | 验收人逐任务核对清单，在登记表填写结论 | 已填写的验收登记表 |
| 7. 关闭 | 出口门禁全部满足，迭代状态置 `CLOSED` | 迭代验收结论 |

### 2.2 任务状态定义

| 状态 | 含义 | 可进入下一状态的条件 |
| --- | --- | --- |
| `TODO` | 未开始 | 上游任务 VERIFIED |
| `DOING` | 开发中 | — |
| `REVIEW` | 已提交评审 | 自测清单全部通过 |
| `VERIFIED` | 已验收 | 验收人完成登记，证据齐全 |
| `BLOCKED` | 阻塞 | 记录阻塞原因与责任人，解除后回到 DOING |
| `WAIVED` | 豁免 | 必须写明豁免理由并经项目负责人确认，不得用于核心功能 |

### 2.3 验收登记规则

1. **登记责任人**：每个任务由非开发者本人验收（交叉验收）；迭代整体由项目负责人验收。
2. **登记时机**：部署验证通过后 1 个工作日内完成登记，禁止批量补登。
3. **必填字段**：任务编号、验收结论（通过/不通过/有条件通过）、验收人、验收日期、证据引用、遗留问题编号。
4. **证据要求**（至少一项，优先多项）：
   - 代码：PR 链接或 commit 号；
   - 自动化：pytest / Vitest / Playwright 执行结果与覆盖率数字；
   - 接口：curl 或 Postman 请求与响应（含 `code` 与状态码）；
   - 页面：关键页面截图（含 URL 与时间）；
   - 部署：预发版本号、部署时间、`/healthz` 返回。
5. **不通过处理**：登记为"不通过"并创建缺陷单（标注 P0–P3），修复后重新走部署验证与登记，原登记追加而非覆盖。
6. **有条件通过**：仅允许遗留 P2/P3 问题，且必须填写遗留问题编号与计划处理迭代；P0/P1 不得有条件通过。

### 2.4 迭代出口门禁（DoD）

| 门禁 | 标准 |
| --- | --- |
| 功能 | 本迭代验证场景全部通过，无 P0/P1 缺陷 |
| 质量 | `ruff check`、`tsc --noEmit`、`eslint` 零错误；新增/修改代码覆盖率 ≥ 80%，核心 service ≥ 90% |
| 契约 | OpenAPI 校验通过，接口变更已同步前端类型 |
| 数据 | 迁移可在空库与存量库各执行一次，可回滚 |
| 部署 | 预发部署成功，`/healthz` 200，重启后服务自恢复 |
| 回归 | 上游迭代的核心验证场景抽测通过（至少 3 条） |
| 登记 | 本迭代任务登记完成率 100%，无未登记任务 |
| 文档 | 新增接口、错误码、环境变量已更新到架构文档或对应说明 |

### 2.5 环境与部署口径

| 环境 | 用途 | 部署方式 |
| --- | --- | --- |
| 本地 | 开发自测 | macOS + `runserver` + `pnpm dev` |
| 预发（staging） | 每迭代部署验证 | Ubuntu 24.04，Nginx + Gunicorn + systemd，独立库 `guda_staging` |
| 生产 | 最终上线 | Ubuntu 24.04，部署结构与预发一致，仅配置不同 |

每次迭代部署必须记录：版本号（commit）、迁移列表、部署人、部署时间、`/healthz` 结果、回滚点（上一版本 commit）。

### 2.6 回滚要求

1. 每个迭代发布前保留上一版本代码目录与数据库备份。
2. 回滚判定：出现 P0 缺陷、`/healthz` 持续 503 超过 5 分钟、核心链路错误率 > 1%。
3. 回滚步骤：切回上一版本代码 → 执行该迭代迁移的反向迁移（不可逆迁移必须提前说明并采用"先兼容后清理"两阶段）→ 重启服务 → 冒烟验证。
4. 回滚后必须在验收登记表追加回滚记录（时间、原因、影响范围）。

### 迭代 I1：会员账号体系

**目标**：打通注册、登录、令牌生命周期与个人基础资料，为后续所有会员接口提供身份基座。

**功能范围**：自定义用户模型、角色组、邮箱验证码、注册、登录、JWT 刷新/登出、登录限流与锁定、找回密码、个人信息与头像、地址管理、前端登录注册与路由守卫。

**不包含**：第三方登录、短信通道、实名认证、账号自助注销。

**独立部署验证场景**：

| 编号 | 场景 | 操作 | 通过标准 |
| --- | --- | --- | --- |
| V1-1 | 注册 | 提交邮箱、用户名、密码，输入控制台/邮件验证码 | 201，用户落库，密码为 Argon2 哈希 |
| V1-2 | 登录 | 用户名 + 密码登录 | 200，返回 access 与 `Set-Cookie: refresh`（HttpOnly） |
| V1-3 | 保持登录 | 刷新浏览器页面 | 自动刷新 access，仍为登录态 |
| V1-4 | 令牌轮换 | 用旧 refresh 再次刷新 | 401 `AUTH_REFRESH_REVOKED` |
| V1-5 | 登录锁定 | 连续 5 次错误密码 | 第 6 次返回 423 `AUTH_ACCOUNT_LOCKED` |
| V1-6 | 找回密码 | 请求重置并完成确认 | 重置成功，旧 refresh 全部失效 |
| V1-7 | 地址管理 | 新增 2 条地址并设默认 | 默认唯一，旧的自动取消默认 |
| V1-8 | 越权 | 用户 A 访问用户 B 的地址 `public_id` | 404 或 403，不泄露数据 |
| V1-9 | 前端 | 登录 → 个人中心 → 地址页 | 页面可用，未登录访问会员页跳登录并回跳 |

### 迭代 I6：支付流程演示

**目标**：在订单之上接通模拟支付闭环，使订单可走到"已完成"，为评价与通知提供真实业务事件。

**功能范围**：支付单复用与关闭规则、模拟收银台、HMAC 签名回调、回调幂等、支付失败重付、订单超时关闭支付单、后台支付流水、前端支付页。

**不包含**：任何真实支付渠道、退款资金原路退回（仅订单状态流转）、对账与结算。

**独立部署验证场景**：

| 编号 | 场景 | 操作 | 通过标准 |
| --- | --- | --- | --- |
| V6-1 | 发起支付 | 待支付订单选择模拟渠道 | 生成支付单，金额与订单应付一致 |
| V6-2 | 支付成功 | 模拟收银台点击成功并回调 | 支付单 `SUCCESS`，订单 `PAID`，商品销量 +1 |
| V6-3 | 回调幂等 | 同一 `payment_no` 重复回调 3 次 | 均返回 200，订单与销量只变更一次 |
| V6-4 | 签名校验 | 使用错误签名回调 | 401 `PAYMENT_SIGNATURE_INVALID`，订单不变 |
| V6-5 | 金额篡改 | 回调金额改为订单应付 -1 元 | 422 `PAYMENT_AMOUNT_MISMATCH`，订单不变 |
| V6-6 | 支付失败重付 | 先失败再成功 | 失败单 `FAILED`，新单 `SUCCESS`，订单最终 `PAID` |

## 6. 变更与例外处理

### 6.1 计划变更

1. 新增需求必须先评估：是否影响当前迭代范围、是否需要数据模型变更、是否引入新依赖。
2. 影响当前迭代的变更：走变更登记（提出人、原因、影响面、批准人），批准后更新本文档对应迭代的任务与验证场景。
3. 不影响当前迭代的变更：登记到"待排迭代"清单，不插队；下一迭代启动时纳入。
4. 已 `VERIFIED` 的任务若因变更需返工，状态回到 `DOING`，并在登记表追加返工记录，禁止覆盖原记录。

### 6.2 阻塞处理

1. 任务阻塞超过一个工作轮次必须标记 `BLOCKED`，写明阻塞点、责任人、期望解除条件。
2. 阻塞不得通过"跳过验证清单"绕过；确需临时绕过，走 `WAIVED` 并记录风险。

### 6.3 文档维护

1. 本文档由项目负责人维护，任务状态、验收登记、汇总表随迭代推进实时更新。
2. 需求或架构变更导致迭代范围调整时，同步更新本文档第 1、3、5 章，并在附录记录变更版本。
3. 上线后本文档作为交付物归档，验收登记表是质量追溯依据，禁止删除历史行。
